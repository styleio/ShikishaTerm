# DB 接続 — 設計メモ（WIP・着手前）

> ステータス: 2026-08-28 時点の合意（**未実装**）。着手前の設計討議の記録であり、
> 現在のコードの説明ではない。「なぜそう決めたか」と「何を却下したか」を残すためのファイル。
> 英語版は [db-access.md](db-access.md)。

## 背景

「DB の中身が GUI で見える・追加できる・編集できるタブが欲しい」という要望から始まった。

端末で表は読めない。`SELECT * FROM users` の結果が 80 カラムの端末で折り返されて崩壊するのは
誰もが知っている苦痛で、ここは GUI が構造的に勝つ領域である。「端末で打てるから不要」は通らない。

## このアプリが作る理由（既存の DB クライアントとの違い）

汎用 DB クライアントは飽和市場で、そこに参入する意味はない。**このアプリにしか出せない価値は
1つだけあり、それが作る理由のすべて**である。

> **AI が DB を触れる。**

無人・承認なしで動いている AI に「テストデータを入れておいて」「このテーブルの中身を見て」と
会話で頼める。どのタブのどの AI が何を変えたかを、このアプリだけが知っている。他のどの DB
クライアントにも原理的にできない。

## 貫く設計思想

**画面 → Lua → DB。** DB アクセスは Lua のプリミティブとして作り、管理タブはそれを呼ぶだけの
薄い GUI にする。Rust 側に「DB クライアントというモード」を作り込まない。

これで得られるもの:

1. 自動化スクリプトから DB を触れる
2. 管理タブがそのプリミティブで組める
3. **AI が DB を触れる**（`run_scoped` の中で）
4. 管理タブ自身をユーザーが Lua で自動化できる

我々が作った成果物が、そのままユーザーの手に渡るレゴのパーツになる。レゴ/プリミティブ原則
（RULES「設計の約束」）に反しないどころか、その素直な適用である。

## 1. 接続は名前付きゲートウェイに乗せる

`caps.rs` の既存の仕組み（"Nothing is allowed by default"、スクリプトはパスや URL を組み立てられず
登録された名前しか呼べない）に、そのまま乗せる。

```lua
db.query("maindb", "SELECT * FROM users WHERE id = ?", { 42 })
```

第一引数は必ず**設定に登録された名前**。接続文字列もパスワードも Lua には渡らない。AI が書いた
Lua が認証情報を抜くことが構造的に不可能で、これは既存の `caps.http(name, body)` /
`caps.browser_click(name, sel)` と同じ形。

資格情報の置き場も既にある（`secrets.json` は Argon2id + AES-256-GCM で暗号化可能）。
**新しい安全機構をゼロから作る必要はない。**

AI が `.lua` を書いて人間経由で走らせ、権限を洗濯する経路も既に塞がっている
（`caps.rs` の `is_forbidden` が `.lua` / `.enc` への書き込みを禁止。コメントに
"prevents self-modification" と明記されている）。

### 設定の形

```jsonc
"db": {
  "maindb":  { "kind": "mysql",  "readonly": true,  "raw_write": "off"   },
  "scratch": { "kind": "sqlite", "readonly": false, "raw_write": "human" },
  "cache":   { "kind": "valkey", "readonly": true }
}
```

- `readonly` — 既定 **true**
- `raw_write` — 生 SQL による**書き込み**の可否。`off` / `human` / `all`。既定 **off**。
  `human` と `all` の区別は `tab.is_model` で判定する（既存のフィールド）
- **生 SQL による読み取りは常に開いている**（後述の理由により、それで安全が保てるため）

天秤（便利さ vs 安全）は**接続ごとに人間が決める**。アプリ全体で 1 点を選ぶ必要はない。

## 2. 層構造 — Core は作る、ORM は作らない

```
層1  db.query(name, sql, params) / db.exec(name, sql, params)   ← 生。土台。必須
層2  db.tables(name) / db.columns(name, "users")                ← 方言差はここに閉じる
層3  db.insert / db.update / db.delete / db.clause               ← 糖衣
────────────────────────────────────────────────────────────
画面  上を呼ぶだけの薄い GUI（webui.rs に 1 ページ）
```

**層1 だけで管理タブは作れる。** 層3 は無くても困らない。層1 から作り、層3 は本当に欲しく
なってから足す（層3 を先に設計すると、そこに引きずられて層1 が歪む）。

### 判定ルール

> **生 SQL に降りられる限り安全。降りられなくなったら地雷。**

`db.query` の生の口が常に隣にあり、`db.insert{...}` はそれを組み立てる糖衣にすぎない — この関係
が保たれている限り、糖衣をいくら足しても壊れない。逆に「`db.insert` があるから `db.query` は
要らない」となった瞬間に ORM 化する。

### 作らないもの（明示）

モデルクラス、リレーション定義、遅延読み込み、変更追跡、マイグレーション。

これらは「どの DB か知らなくていい」という**約束**を売るものであり、その約束は JOIN・型・
トランザクション・非関係モデルで必ず破れる。破れると結局生 SQL が必要になり、**翻訳層と生の口の
両方を保守することになる**。

## 3. `where` の書き方 — 演算子を発明しない

等価比較しかできない `where` は使い物にならない（`created_at < ?` も LIKE も OR も範囲も
書けないのは論外）。かといって演算子の語彙を自作すると、際限なく育つ。

**答え: 演算子は SQL に任せ、ビルダは機械的な部分だけ担当する。**

1 つのテーブルに 3 種類の条件を混ぜられるようにする:

```lua
db.clause({
  id = 12,                          -- 列 = 値      → `id` = ?
  status = db.list({ 3, 4 }),       -- リスト        → `status` IN (?, ?)
  { "created_at < ?", ts },         -- 断片 + 束縛値
  { "name like ?", "%" .. q .. "%" },
})                                  -- 既定 AND、{ operator = "OR" } で OR
```

これで `created_at < ?`・LIKE・OR・BETWEEN・IN が全部書ける。**表現力は SQL と同じ**。

### 束縛の記法

- `?` — **値**を束縛する
- `??` — **識別子**（テーブル名・カラム名）を束縛し、方言ごとの引用符を付ける

方言差は実質この 3 つしかない: 識別子の引用符（`` `x` `` / `"x"` / `[x]`）、LIMIT の書き方、
RETURNING の有無。MySQL と SQLite の差は極めて小さい。

### 補助

`db.list{...}` / `db.raw("count + 1")` / `db.NULL`

### 生断片と SQL インジェクション

`{ "name like '%" .. user_input .. "%'" }` と書けばインジェクションが成立する。これは
**逃げ道を用意した以上、避けられない性質**である（同種のビルダはすべてこの性質を持つ）。

正しい書き方は `{ "name like ?", "%" .. user_input .. "%" }` — **ワイルドカードは SQL 側ではなく
パラメータ側に置く**。

Lua にはタグ付きテンプレート（補間が自動的に束縛パラメータになる仕組み）が無いため、
言語機能で塞ぐことはできない。したがって:

- **主防御にはしない。** 引用符の禁止も静的検査も「推測」であって「判定」ではない
- 事故を減らす**補助**として、読み込み時（既に `load()` で構文検証している）に
  `db.*` の引数内の `..` を警告する
- **本当の守りは §4**。注入が成功しても、その接続に許された範囲を超えられない

## 4. 安全の保証をどこに置くか（この設計の中核）

### 満たすべき要求

1. **読みの口から DDL/DML が絶対に通らないこと。** ユーザーがどんな文字列を書いても、
   どんなに拙くても。フールプルーフであること
2. **基本的な条件式が書けること。** 複雑な集計や多段 JOIN は諦めてよいが、
   `created_at < ?`・LIKE・OR・範囲が書けないのは論外

この 2 つは両立する。

### 保証はエンジンに置かない

各 DB エンジンは、それぞれ読み取り専用を強制する機構を持っている。しかし
**「A にはこれがある、B にはこれがある」と並べたものは設計ではなく、ただの機能リスト**である。
その形にすると:

- DB を 1 つ足すたびに、保証が**黙って**下がりうる
- 上流が仕様を変えたとき、**誰も気づかない**
- そもそも「保証とは何か」を一言で言えない

### 保証は、我々が所有するものに置く

**ドライバの trait である。**

```rust
trait Db {
    /// 書き込めない接続を開く。エンジンによる強制であること。
    /// 実装できないドライバは登録できない
    fn open_readonly(&self, cfg: &Cfg) -> Result<Conn>;
    fn open_readwrite(&self, cfg: &Cfg) -> Result<Conn>;
}
```

**`db.query` は必ず `open_readonly()` の接続で走る。**

これにより「新しい DB を足すとき、読み取り専用の対策を忘れないようにしよう」という
**レビューの心がけ**が、「実装しないとコンパイルが通らない」という**構造**になる。

各エンジンの機構は**契約の実装**であって、契約そのものではない:

| DB | 読み取り専用の強制 | 文/コマンドの分類 |
|---|---|---|
| SQLite | 読み取り専用フラグで開く（別ハンドル） | 準備済み文が書き込むかをエンジンに問う + 認可コールバック |
| MySQL | アカウント権限 | prepare 応答のカラム数（0 なら結果セットを返さない文） |
| PostgreSQL | 読み取り専用トランザクション / 専用ロール | （実装時に確定） |
| Valkey | ACL（`+@read -@write -@admin -@dangerous`、`~key:*` でキー範囲も） | コマンド情報の readonly フラグ |

いずれも**分類するのはエンジンであり、我々の正規表現ではない**。これが「どんな文字列でも
突破できない」の根拠になる。

### 上流の仕様変更を捉える方法は、テストしかない

推論でもドキュメントでもなく、**適合テストの束**を作り、全ドライバに同じものを通す。
**実際の DB インスタンスに対して CI で回す。**

SQL 系:

```
読みの口に "DROP TABLE t"              → エラー。t が存在し続けること
読みの口に "INSERT INTO t ..."          → エラー。行数が変わらないこと
読みの口に "UPDATE t SET ..."           → エラー
読みの口に "SELECT 1; DROP TABLE t"     → エラー（多重文を有効にしない）
読みの口に "CALL p()"（中で書く）        → エラー
読みの口に ファイル書き出し系の SELECT   → エラー
読みの口に 複雑な SELECT（JOIN/集計/CTE）→ 成功すること
```

KV 系:

```
読みの口に 全消去コマンド        → エラー。キー数が変わらないこと
読みの口に 削除・設定コマンド    → エラー
読みの口に 書けるスクリプト実行  → エラー
読みの口に 読み取り専用スクリプト → 成功すること
```

**上流が挙動を変えたらテストが赤くなる。** これがあって初めて「保証できるのか」への答えが
「はい、この N 本のテストが全ドライバで緑だからです」という**確認可能な形**になる。

### エンジン判定を補う、安いトークン検査

MySQL のカラム数判定は `CALL some_procedure()`（結果セットを返しつつ中で書ける）で抜ける。
そこで**先頭トークンが `SELECT` / `WITH` かの安い検査**を重ねる。

トークン検査は単体では脆いが、ここでは**主防御ではなく補助**なので脆さが問題にならない。
逆にエンジン判定だけでは `CALL` が抜ける。**独立した 2 つの検査を重ねる**のが答え。

### この方式が where 句に制限をかけないこと

読みの口では **SQL の読み取り機能を 1 つも削らない**。JOIN も GROUP BY も CTE もサブクエリも
使える。制限しているのは「書くこと」であって「書き方」ではない。

要求 1 と要求 2 が両立するのは、この性質による。

## 5. 意図しない大量更新・削除を防ぐ

`WHERE` の有無を検査する方式は採らない。`WHERE 1=1` も `WHERE id > 0` も
`WHERE id REGEXP '^[0-9]+$'` も全件であり、「この条件は全件か」は一般に判定不能。
**どんな構文チェックも壁ではなく段差**である（WHERE 必須は**タイプミス除け**と呼ぶのが正しく、
悪意を防ぐものではない。それでも事故の大半はタイプミスなので価値はある）。

**DB に依存しない方法を採る:**

```
BEGIN
  UPDATE / DELETE を実行
  → 影響行数を取得
  多すぎる／確認されていない → ROLLBACK
  確認済み                   → COMMIT
```

- MySQL でも SQLite でも同一に動く
- 実行計画からの推測ではなく、**実際に何行動いたかを数える**
- ビルダー経由なら、同じ条件で `SELECT COUNT(*)` を先に投げて**実行前に**確認を出せる

**trait の必須メソッド**にする。トランザクションを提供できないドライバは、書き込み可能な接続と
して登録できない（例: レプリカセットでない構成の一部の DB は自動的に読み取り専用にしかならない。
人間が気をつけるのではなく、型が拒否する）。

**SQLite の安い保険:** ファイル 1 つなので、`readonly: false` の SQLite はそのセッションで最初に
書き込む直前にコピーを取れる。ほぼ無料で、全部の防御を抜けた事故から復帰できる。
「壊れないようにする」で頑張り切るより、「壊れても戻せる」を 1 つ持つ方が筋が良い。

## 6. SQL でない DB（Valkey など）

**対応する。ただし `db.*` には載せない。**

Valkey は SQL ではなく、テーブルも行も列もない。`db.query(name, sql)` を無理に被せると
抽象が初日から漏れる。**別プリミティブにする**（同じ判断を MongoDB にも適用する）。

```lua
kv.scan("cache", "user:*")                     -- キー一覧
kv.type("cache", "user:42")                    -- string / hash / list / zset ...
kv.get("cache", "user:42")                     -- 型に応じた値
kv.ttl("cache", "user:42")
kv.command("cache", { "HGETALL", "user:42" })  -- 生コマンド（readonly のものだけ）
```

**契約（`trait Db` と適合テスト）は共通、呼び口だけが別。** レゴのパーツが 1 個増えるだけで、
既存のパーツは何も曲がらない。

Valkey は trait を**むしろ綺麗に満たす**: ACL をアプリ側から発行でき、キーのパターンまで絞れる。
「ユーザーが読み取り専用アカウントを作ってくれるか」に依存しない点で MySQL より強い。

### GUI の骨格は共通

| SQL タブ | KV タブ |
|---|---|
| テーブル一覧 | キー一覧（`:` で木にする） |
| 行のグリッド | キー ＋ 型 ＋ TTL の表 |
| セルの値 | 型別ビュー（hash → 表、list → 表、zset → score 付き） |
| SQL 実行欄 | コマンド実行欄 |

「一覧 → 1 件の詳細 → 自由入力欄」という同じ骨格なので、画面の作りを使い回せる。

## 7. 対応範囲の方針

> **対応 DB は、増やせるものではなく、選んだものにする。**

`trait Db` を実装し、適合テストが全部緑になったものだけが載る。「設定を書けば何でも繋がる」
にはしない。**保証を維持できる範囲が、そのまま対応範囲**である。

着手順:

1. **SQLite** — サーバー不要、認証なし、ファイル 1 つ。読み取り専用の強制が最も厳密。
   Windows は SQLite の CLI を同梱しないので、外部 CLI に頼る案が成立しない
   （＝内蔵する価値が最も高い）
2. **MySQL** — 同期のピュア Rust ドライバがあり、非同期ランタイムを持ち込まずに済む
3. **Valkey** — SQL 系が固まってから、`kv.*` として
4. **PostgreSQL** — 適合テストが緑になったら

「対応してる DB は？」には「MySQL / SQLite」と最初から書く。実装コストではなくサポートコスト
の話なので、明示すれば済む。

## 8. 却下した案と、その理由

### 汎用 DB クライアントを Rust に内蔵する（最初の案）

**却下。** ただし当初挙げていた反対理由のうち、以下は**誤りだったので取り下げた**:

- 「非同期ランタイムを引き込む」— 誤り。SQLite も MySQL も**同期専用**のピュア Rust ドライバが
  あり、非同期ランタイムは不要。仮に入っても同期 API の裏に閉じ込められる
- 「DB ごとの保守が永遠に増える」— スコープを固定すれば現実的。実作業量は数百行 + 1 ページ

**残る理由**は「レゴ原則に反する（Rust の作り込みモードが増える）」の 1 点だったが、
**それは §「画面 → Lua → DB」構成によって消えた**。プリミティブ 1 個 + 薄い GUI であれば
原則に反しない。

### 既存の Web ベース DB 管理ツールをブラウザタブで開く

**却下。** 「開発者は既にどれかを動かしている」という前提が成り立たない。
サーバー側でアプリを動かしてローカルで編集している構成では、そのランタイムはローカルに無い。
別言語 + 別 DB の構成なら、使わないランタイムを 1 つ増やせと言うことになる。

「タブの中に置く」と「ランタイムを増やさない」を同時に満たせるのは内蔵だけ、というのが結論。

### DB 自身の CLI を叩いて TSV を表として描く

**却下。** ドライバを実装せずに済み方言も CLI に任せられる利点があったが、

- **SQLite で成立しない。** Windows は SQLite の CLI を同梱しないので、他言語経由で SQLite を
  使っている環境にはそれが無い
- TSV 解析に地雷がある（BLOB、NULL と空文字の区別、値に含まれる改行）

### `WHERE` 必須チェック

**却下**（§5 参照）。セキュリティ機能ではなくタイプミス除けであり、影響行数による方法に置き換える。

### 生断片の引用符禁止・静的検査を主防御にする

**却下**（§3 参照）。推測であって判定ではない。補助としてのみ使う。

### 「エンジンの機能で守る」を保証にする

**却下**（§4 参照）。DB を足すたび保証が黙って下がり、上流の変更に誰も気づかない。
