# 配った仕事の記録（orchestration.db）

> English version: [orchestration-db.md](orchestration-db.md).
> 今のテーブルの定義: [orchestration-db.sql](orchestration-db.sql)（テストが書き出します。手で直さないでください）。

1つの AI のタブが、仕事の一部をほかの AI のタブに配るとき（`shikisha job_open`・`assign`・`report`・`inbox` など。[AUTOMATION.ja.md](../AUTOMATION.ja.md) の「オーケストレーション」を参照）、アプリは「誰に何を配ったか」「何が返ってきたか」「何がまだ残っているか」を SQLite のファイルに記録します。ファイルはアプリの状態フォルダの `orchestration.db` です。コードは `crates/core/src/orch/db.rs` にあります。

## テーブルごとの役目

| テーブル | 1行が表すもの | 記録する理由 |
|---|---|---|
| `jobs` | 人が1つの AI のタブ（依頼元）に最後まで回すよう頼んだ依頼 | 依頼元の会話が途切れたり要約されたりしても、`job_status` で進み具合を確かめられるようにするため |
| `tasks` | 依頼の中の1つの作業と、その作業が待つ作業 | 待っている作業が終わってから、その作業を着手できるようにするため |
| `assignments` | 1つのタブによる、1つの作業の1回の取り組み | 報告を、作業を割り当てたタブの、割り当てたときのプロセスからだけ受け付けるため。やり直しには別の行を作ります |
| `opened_tabs` | 依頼が自分で開いたタブ | 依頼が閉じるタブを、自分で開いたタブに限るため。人が入力したタブは閉じません |
| `made_folders` | 依頼が作った作業フォルダ（git worktree） | 誰も使っていない作業フォルダを知らせるため |
| `mail` | 依頼元と担当のあいだで伝えた1件の連絡 | 読む側が作業中でも、伝えたことを失わないため |
| `handovers` | 読む側に渡した連絡のまとまり。読む側が「対応した」と伝えるまで残ります | 読む途中で途切れた側に、同じ連絡を渡し直すため |
| `questions` | 依頼元の答えを待っている担当の質問 | 担当がまだ待っていても、もう待っていなくても、答えを担当に届けるため |
| `decisions` | 依頼元か人が決めるまで止めておく作業 | たとえば main へのマージを、人が決めるまで待たせるため |
| `raised` | 見張りがすでに知らせたこと | 同じことを1回だけ知らせるため |

`meta` には `schema` の1行だけがあり、ファイルの版を表します。

状態（`state`・`held_by`・`afterwards` など）は、ただの文字列です。テーブルには CHECK 制約を付けていません。どの状態からどの状態へ移ってよいかは、コードの1か所（`Store::shift`）で決めます。`Store::shift` は、行がまだ想定どおりの状態にあるときだけ書き込みます。そのため、新しい状態を足す作業は、テーブルを作り直す作業ではなく、コードの1行を足す作業になります。

## テーブルを変える手順

テーブルは、番号付きの手順で作り、番号付きの手順で変えます。出荷した手順は書き換えません。

1. **手順を足す。** 普通の変更は、`crates/core/src/orch/migrations/NNNN_内容.sql`（次の番号を4桁で）のファイルを作り、`db.rs` の `STEPS` の末尾に1行足します。

   ```rust
   (2, "what", Step::Sql(include_str!("migrations/0002_what.sql"))),
   ```

   SQLite がその場で変えられない変更（列の型や制約を変える、列を消す、列の位置を変える）は、`Step::Code` で関数を書き、その関数から `rebuild(...)` を呼びます。`rebuild` は SQLite の公式文書のとおりに作り直します（新しいテーブルを横に作り、行を写し、古いテーブルを消し、新しいテーブルの名前を変え、索引を作り直します）。行の中身を変える変更も `Step::Code` で書きます。
2. **出荷した手順は書き換えない。** その手順をすでに実行したファイルは、同じ手順をもう一度実行しません。書き換えると、ファイルとコードの食い違いがずっと残ります。
3. **設計図を書き直し、何が変わったかを確かめる。**

   ```
   SHIKISHA_WRITE_DOCS=1 cargo test -p shikisha-core orchestration_db
   ```

   書き直すまで、テスト `the_orchestration_db_design_is_what_the_steps_make` が失敗します。
4. **行が入っている記録で手順を試す。** テスト `an_older_record_is_copied_then_brought_up_to_date_with_its_rows` と同じように確かめます。

## 利用者の PC で起きること

- 手順は1つずつ別のトランザクションで実行し、終わるたびに版を記録します。途中でアプリが落ちても、次の起動では止まった手順からやり直します。失敗した手順は何も残しません。
- すでにテーブルがあるファイルを変える前に、そのファイルを `orchestration.db.v<版>.bak` として隣に写します（`VACUUM INTO`）。元に戻すときは、そのファイルを元の場所に置きます。
- 手順を実行しているあいだは外部キーを切ります（作り直しでは、ほかのテーブルが指しているテーブルを消すからです）。代わりに手順ごとに外部キーを確かめ、何も指していない行を残す手順は失敗させます。
- 新しい版のアプリが書いたファイルは、変えずに断ります。古いアプリには、新しいアプリがその内容で何を表したかが分からないからです。
- 閉じた依頼は、閉じてから30日たつと、その依頼に属するものと一緒に消します。
