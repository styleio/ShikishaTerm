# 便利機能バー（呼び出し式サブ入力欄）— 設計メモ（WIP）

> ステータス: 2026-08-20 時点の合意（着手前）の設計討議の記録。
> ここに書いた大半はその後コンポーザーとして実装済みで、このファイルは現在のコードの説明ではなく
> 「なぜそう決めたか」の記録として残す。英語版は [convenience-bar.md](convenience-bar.md)。

## 背景・目的

現在サブ入力欄はモバイル専用（スマホのキーボードが入力欄を隠す問題への対処として生まれ、`castMode` で「ブラウザ操作リレー」か「端末」かに送り先を切替えている）。これを **PC でも使えるようにし、その上に便利機能（添付・定型文/マクロ・対象タブ操作）を載せる**。

## 貫く設計思想

- **プリミティブ × 薄いGUI × 種別ディスパッチ**。Rust側に「モード」を作り込まず、既存プリミティブ（`send_to_tab` / `browser_fill` / `browser_press` など）の上に薄いGUIを重ねる。増やすのはGUIとプリミティブだけ。
- **合体関数を作らない**。独立プリミティブを足して Lua で合成させる。
- 迷ったら「宣言（設定に保存した値）」ではなく「実行時の現実」を見る。

## 0. PC でのサブ入力欄 — 「常設」ではなく「呼び出し式」

**決定: PC ではトグル/ホットキーで呼び出す。常設しない。直打ちが既定のまま。** モバイルは従来どおり常設（キーボードが隠す問題があるので正当）。

理由（PC 常設のデメリット）:
- 入力経路の二重化。PC は端末直打ちが最速・最確実。常設バーは「どっちに打つ?」の迷いと、バー→PTY注入の往復（遅延・ズレ）を生む。TUI（vim / less / pager 等）に整形済みブロックを注入すると壊れる。
- 画面（縦）を食う。モバイルと違い PC では純コスト。
- フォーカス/キー競合（Ctrl+B プレフィックス・マウス・IME）。モバイルで `if REMOTE return`（focus）と戦っているのと同種。
- Rust 側で作り込むとバー自体が「モード」化し、思想に反する。

→ バーは主役ではなく **便利機能の器**。呼び出し式にして直打ちの良さを保つ。

## 1. ファイル添付

### 前提の確認（合意）
端末CLIはGUIチャットのような“添付”ができない。**ファイルを置いてパス（または `@path`）をAIに渡す**のが実際の流儀（Claude Code の `@file` / 画像パス読み込み、Aider のファイル指定等）。よって「貼り付け→tmpに保存→絶対パスを入力欄に出す」は王道で正しい。

### 動作
貼り付け / ドラッグ / 添付ボタン → 保存 → 入力欄に対象が読めるパスを挿入。

### 保存先
- **原則: 対象タブの作業フォルダ(cwd)配下 `<cwd>/.SHIKISHA/tmp/`**（cwd配下だとAIが確実に読める。中央フォルダだとAIのサンドボックスがcwd外読取を拒否することがある、というトレードオフを踏まえての選択）。
- **gitignore はリポジトリ任せにしない**: 作った `.SHIKISHA/` の中に `*` だけ書いた `.SHIKISHA/.gitignore` を必ず置く。親がgitでもgitでなくても配下が無視される（自己完結）。
- 注意: cwd はタブごとに任意。「SHIKISHAの実行フォルダ」ではない。

### ファイル名 — 強制的にこちらで生成
- **ユーザー入力名はサニタイズせず、こちらでランダム名を生成**（サニタイズはいたちごっこ、生成は安全側。マルチバイト・衝突・パストラバーサルがまとめて消える）。
- 名前は **単純なランダム**でよい（重複排除の用途はないので内容ハッシュ不要＝大きいファイルの全読みコストを避ける）。
- 拡張子は後述の判定に従う。読みやすさが欲しければ先頭に無害化した元名を足すのは任意。

### 型判定（マジックバイト）— 役割は限定的、過信しない
判定の役割は「型を正しく当てること」ではなく、価値の重心は次の2層構造:
1. **実行ファイル系マジックの拒否**（MZ / ELF / Mach-O / シェバン等）＝曖昧さゼロで確実に効く。「画像のつもりが実行体」をここで弾く。
2. 既知型（PNG/JPEG/GIF/PDF）に一致 → **その判定拡張子を採用**（明白な誤ラベル訂正）。
3. **不明**（SVG等テキスト系・マイナー形式）→ 危険マジックでない以上ほぼ不活性 → **元拡張子のまま受理でOK**。

「不明で元拡張子に戻す」は判定の意味を薄めない。意味は(2)の当てっこではなく(1)の危険拒否にあり、そこは不明ケースと独立に堅い。

### 偽装（スプーフィング）についての立場 — 「全部弾く」には明確に反対
- **保存＝実行ではない**。バイト列を書いても何も起きない。うちのアプリは保存してパス文字列を渡すだけで**絶対に起動しない**。OSも拡張子で勝手に実行しない。
- 「危険なファイルを門前で全部弾く」は**完全には実現不可能**で、むしろ誤った安心感を生む（どんな画像もパーサ脆弱性次第で危険になりうる＝拡張子では防げない）。
- 本当に効く守り＝「ディスク上で不活性」「触るのは“ユーザーが選んだそのAI”だけ（そのAIは既にcwd全体を触れる＝限界コスト小）」という構造そのもの。
- **AI時代の本命脅威はプロンプトインジェクション**（画像/PDFに指示を仕込みAIが従う）。添付を簡単にすると入り口が増える。「AIに渡すファイルは信用の対象」という前提は崩さない。
- → 結論: **「全部弾く」ではなく「不活性のまま保存＋実行体マジックは拒否＋絶対に実行しない＋掃除する」**。

### 設定項目
- サイズ上限（基本設定で変更可）。
- 対応拡張子の初期セット（例: jpg/png/gif/pdf）。危険承知の上級者は増やせる（実行しない前提なので許容）。

### tmp の掃除
起動時/日次などで古いものを消すポリシーを検討。

### 種別ごとの“届く形”（重要）
統一すべきは**概念（対象が読めるパスを渡す）**で、**手段は種別で分ける**。「全部SCPで統一」は反対（ローカル/WSLはコピー不要なのに sshd 依存・再認証・遅延を足すだけ）。
- **ローカルタブ**: コピー不要。cwd配下に置いてそのパス。
- **WSLタブ**: コピー不要・**パス変換で解決**。ただし `/mnt/c` 決め打ちは危険（`/etc/wsl.conf` の `[automount] root=` で変更可、UNC非対応）。**`wsl.exe -d <distro> wslpath -a -u "<winpath>"` に変換を委譲**（automount設定を尊重、WSL1/2吸収）。distro は起動コマンド/プロセスから、無指定なら既定distro。
- **SSHタブ**: 本物のアップロードが要る。**後段フェーズ**。ただの SCP ではなく:
  - 認証: 別プロセスの scp は再認証（鍵/パスワード/2FA）になりうる → **OpenSSH の ControlMaster（接続再利用）**で回避（ssh起動に `-o ControlMaster=auto -o ControlPath=…` を付け、その socket を scp/sftp で使い回す）。起動コマンド拡張が必要。
  - リモートcwd不明 → 置き先は `~/.SHIKISHA/tmp/` 等の固定に。
  - 掃除・権限・作成も必要。

## 2. アクション（定型文 / Lua マクロ）

### 決定: 概念とUIは1つ、ペイロードは2種類
- **概念/UI/一覧/フォルダ分けは1系統**（「アクション」＝クリックで発火する登録項目）。
- **ペイロードは `text`（そのまま挿入/送信・初心者向け・高速・エスケープ不要）か `lua`（発火・上級者）の2種類**。
- **文字列を“Luaソース”に変換して保存するのは地雷**（記号やクォートでLuaが壊れる）ので、テキストは literal データのまま保持する。

### 上級者モードは「1定型文ごと」
- グローバルではなく **各アクション独立**に text / lua を切替（項目ごとの「上級(Lua)」チェックでその1個だけ中身の種別が変わる）。グローバルモードにしない方が整合的。

### 実装の下地
既存の `send_to_tab` / オートメーション（scoped Lua sandbox）に薄いGUIを2枚（「定型文」と「スクリプト」）被せる形。

## 3. 対象タブ操作（AI生成Lua）— 最難関・最後・オプトイン

### イメージ（ユーザーの想定フロー）
1. Aタブの便利機能で操作対象タブ（B: ブラウザ）をプルダウンで選ぶ。
2. AタブのAIに自然言語で「Bでgoogle検索して俳句のwikipediaへ」→ **AのAIがLuaを吐いてBを操作**。
3. 対象をC（別AI）に切替 → 「CでXして」→ AのAIがLuaでCを操作。

これはラリー（AI頭脳が返信の```luaを吐く→抽出→scoped実行）の一般化。抽出＆スコープ実行の土台は既にある。

### 重要: ユーザーがLuaを書くのではなく AI が書く
- ユーザーは自然言語で頼むだけ。Luaは対象の種別に応じたプリミティブでAIが生成。

### 状態の渡し方 — 「初回はソフト側で先読みしてファイル化」
- 素朴案（プロンプトに「まず読取してから操作」と書く）は**必ず1往復を無駄にする**。
- **改良（採用）: 読取(状態取得)はAI判断が要らない決定的処理**なので、**ソフト側(Rust)が読取プリミティブ（ブラウザ=DOMダンプ / AIタブ=直近トランスクリプト）を先に実行してファイルに落とし、プロンプトは「このファイルを見て操作して」**にする＝初回の往復が消える。ファイル受け渡しは討論・ブラウザで実績のある手法。
- 但し書き: どの読取を叩くかは対象の種別に依存（＝種別判定と噛み合う）。状態は陳腐化しうる（SPA等）→初回は先読みで良いが、操作後の検証/再試行では結局ループが要る（「初回だけ先読み、以降必要時のみラリー」）。DOMダンプは巨大化しうる→将来は間引き版（アクセシビリティツリー等）。

### 「ブラウザ操作モード」を任意タブへ一般化（長年の“気持ち悪さ”の解消）
- ブラウザ専用の“モード”はプリミティブ原則に反する、というのは正しい直感。
- **正しい形: タブは種別(kind)を持ち、操作機能は対象タブの種別から使える道具箱を導出する**。ブラウザは特別ではなく「browser_* を持つ種別」の一例。AI/端末タブは「send/読取 を持つ種別」。設定の「ブラウザ操作」トグルは“このタブの種別＝ブラウザ(WebView)”という**種別選択**に読み替わる。
- **但し書き（機構は一枚岩ではない）**: 統一できるのは**概念・UI・Lua語彙のディスパッチ**。内部機構は種別で本質的に違う（ブラウザ=CDP/DOM、pty=キー入力/出力スクレイプ）。「見た目とLua語彙は種別で切替わる一つの機能、中の配線は種別ごとに別」。
- **ブレーキ必須**: ログイン済みブラウザをAI生成Luaが操作＝誤送信/削除の危険。ラリー同様の抑制（連鎖上限・緊急停止・ブラウザ送信前の確認）。

### DRY: `operate(A→T)` エンジンを1本化（既存「ブラウザ操作モード」と共通化）

コード確認: 今の「ブラウザ操作」はモードというより既にプリミティブ（ブラウザタブ=`browser <url>`でWebView化、`browser_open/find/click/fill/text`（caps.rs）をLuaが名前指定で叩く。ラリー/オートメーションと同じ土台）。これと便利バーの対象操作は**同じ操作**なので、中身を1つにする（DRY）。ただし“3層”に分けて適用する:

1. **プリミティブ層（`browser_*` / `send_to_tab` ＋ scoped Lua）= 既にほぼ共通**。新設不要。
2. **オーケストレーション層（元AがLuaを生成して対象Tを操作する一連）= ここを1本化**。`operate(source A, target T, 依頼文)` という1エンジン。便利バー用に別実装を作らない。
3. **入口とkindアダプタ**:
   - 入口は2つ・エンジンは1つ: 「ブラウザ操作モード」設定 = **targetを永続固定(sticky)**、便利バー = **その場で一時指定(transient)**。違いは target が sticky か transient かの**薄いパラメータ**だけ。
   - **kindアダプタは別のまま（重複ではなく必要な差異）**: ブラウザ=CDP/DOM、pty=キー入力/出力読取。②が対象種別でアダプタを選ぶ。

DRYの誤用（表面が似てるだけの物を無理に潰す）を避けるため、**②だけ1本化・①は流用・③は薄い分岐**。副作用として、既存「ブラウザ操作モード」は `operate(A→T)` の sticky 版という一般形の特例に吸収され、“ブラウザ専用モード”という気持ち悪さが消える。

### 発火タイミング（レディネス）— operateエンジンの前提条件

未成熟な対象を操作すると事故る（空DOM・描画途中・pty出力途中・AI思考中）。**transient/sticky問わず同じ問題**（起動直後に素早く操作すれば sticky でも壊れる）＝レディネス確認は**共通operateエンジンに置く**（1回直せば両入口が守られる＝DRYの追加利得）。

判定シグナルは既存を再利用（種別ディスパッチ）:
- **pty/AIタブ**: アプリの状態検出（Working/BUSY/DONE/ASK）。**DONE/アイドルまで待って**から先読み＆操作（ラリーが相手のターン完了を待つのと同じ）。
- **ブラウザタブ**: CDPの load / `document.readyState==='complete'`（＋任意でネットワークアイドル）。

**正直な限界（“ready”は完全には定義できない）**:
- SPAは `load` 後も非同期描画 → エンジンのゲートだけに頼らず、AIが吐くLua側も **wait-for-selector 等の防御的プリミティブ**を併用（半分エンジン・半分Lua）。
- 素のシェルの「出力終わった?」はプロンプト検出頼りで曖昧（AIタブは状態検出が堅い、生シェルはヒューリスティック）。
- 起動直後は対象のWebView未生成もありうる。

**on-timeout の方針（＝中止をシステム既定にしない）**:
- 「安全のため中止」を既定にすると**頻繁に止まる“使えない”システム**になる（ユーザビリティ優先で却下）。かといって**毎回モーダルで問うのは割り込み疲れ**。
- 落とし所: **on-timeout の挙動をユーザーの基本設定にする（`進める / 都度聞く / 中止` から選択）**。一度決めれば以後その通り＝選択権はユーザー、毎回の割り込み無し。
- **そもそもタイムアウトを稀にする**：検出をちゃんと作り、種別ごとに余裕のあるタイムアウトを置く。タイムアウトは常用ロジックではなく**バックストップ**（選択が出るのは例外時だけ、通常は黙って通る）。
- **「進める」は kind-aware**（“進める”＝garbage にしない）:
  - ブラウザ: 進めても **AIのLuaの wait-for-selector（自衛）** とセットで「要素が出るまで待って触る」。
  - AI/pty がまだ思考中: 「今すぐ進める」＝半端出力への操作でダメ → この場合の「進める」は **“終わったら実行するようキュー”** の意味にする。
- 注意: 「N秒で完了扱い」が成立するのは主に**ブラウザのload**。**AI/pty は DONE まで待つのが正常**で、時間だけで“完了扱い”にはしない（長すぎは中断/キュー）。

→ `operate(A→T)` の手順: **①レディネス待ち（種別ディスパッチ）→ ②状態を先読みしてファイル → ③AIにLua生成 → ④実行 → 必要なら再読込ループ**。「エンジンのゲート＋AIのLuaのwait＋on-timeoutはユーザー既定(進める/聞く/中止)」で、安全と使い勝手を両立させる。

## 4. 横断課題: 「種別」をどう認識するか

用語を2軸に分解:
1. **構造的種別（ブラウザ or 端末）= 既知**。ブラウザ=WebView(CDP)、端末=ConPTY として別物生成。UI状態に `kind:"browser"` が乗る。推測ゼロ。
2. **端末タブの中身（ローカル / WSL / SSH / AI）= 未記録**。**コマンド文字列からの推測は禁止**（エイリアス・ラッパー・シェル関数・「素のbashに後からssh」で破綻）。

### 方針: 宣言ではなく“実行時の現実”を見る
- **端末タブの PTY 直下の子孫プロセスの実行イメージ名を、必要な瞬間（添付時/操作時）に辿る**。`wsl.exe` があればWSL、`ssh.exe` があればSSH、なければローカル。
  - エイリアスに強い（`alias k=ssh` でも実体は `ssh.exe` を exec）。「素の端末に後からssh」も、その瞬間ツリーに `ssh.exe` が居れば拾える → 「種別を選ばず直打ち」問題が自然に解決。
- **AIかどうか**は別ソースで既知: タブの **profile（claude/codex/gemini…）**。
- **基本は記録しない**。構造(1) + profile + 実行時プロセスツリー、で必要な瞬間に導出（宣言を保存しないから「直打ちしたらどうなる」問題が消える）。保存するとしても任意の上書きヒントだけ。

### 正直な限界
- プロセスツリー走査は Windows 実装が地味に面倒（conhost/OpenConsole が挟まる、権限、レース）、多段ssh/mosh等は取りこぼす、SSHのリモートcwdはツリーから分からない。
- → 取れない時は**ローカル扱い＋手動上書き**を用意。完璧ではないが文字列推測より桁違いに堅い。

## 実装順（合意）

1. **ファイル添付**（具体的価値が最大・低リスク）。「不活性保存＋実行体マジック拒否＋型判定拡張子＋非実行＋掃除」、まずローカルタブ、WSLは `wslpath` で即対応、cwd配下＋自己gitignore。SSHは後段（ControlMaster + sftp/scp → `~/.SHIKISHA/tmp`）。
2. **アクション一覧**（項目ごと text/lua 切替、フォルダは後回し）。
3. **バーの PC 呼び出し式化**（1・2 の器。常設にしない）。
4. **対象タブへ AI 生成 Lua**（種別で道具箱切替＋状態先読みファイル＋ブレーキ。最難関・最後・オプトイン。ベストエフォート前提）。

## オープン論点（未決）

- 添付: 保存先を cwd 配下で確定してよいか（AI読取確実性 vs 任意フォルダ汚染のトレードオフ）。
- 添付: サイズ上限の初期値、対応拡張子の初期セット。
- 添付: tmp 掃除のタイミング。
