# git 操作 — 設計メモ

> ステータス: 2026-09-01 の合意。**層1（プリミティブ）から実装中**。
> 「なぜそう決めたか」と「何を却下したか」を残すためのファイル。
> 英語版は [git-access.md](git-access.md)。

## 背景

「基本的なことは画面でできて、高度なことはコマンドで」という要望から始まった。

git 管理 GUI は一度ボツにしている（2026-08-28）。当時の理由は3つで、そのうち2つは今も生きて
いる制約、1つは既に解消した:

1. **`repo.rs` は git を起動しない**。`.git/HEAD` を直接読むので、rebase 中でロックが握られて
   いても答えられる。git を起動した瞬間その保証を失う → **今も生きている。§6 で扱う**
2. **無人で走る AI のフォルダに破壊的なボタンを置くことになる** → **解消した**。
   自動化の権限（人間/AI の2列）ができたので、`git_*` は既定で人間だけが呼べる
3. **汎用 git クライアントの再発明** → **範囲を「基本だけ」に絞ることで回避する**。§3

## このアプリが作る理由

汎用 git クライアントは飽和市場で、そこへ参入する意味はない。**このアプリにしか出せない価値**
だけを作る:

> **その作業をしていた AI が、そのまま書き、そのまま直す。**

コミットメッセージは、変更を書いた当人が書く。コンフリクトは、片方を書いた当人が解いて、
**人が差分として見てから**入る。他の git クライアントは、AI を呼ぶことはできても
「いま隣のタブで動いている、この変更を書いた AI」を知らない。

## 貫く設計思想

**画面 → Lua → git。** git 操作は Lua のプリミティブとして作り、GUI はそれを呼ぶだけの薄い層に
する。Rust 側に「git クライアントというモード」を作り込まない（RULES のレゴ/プリミティブ原則）。

DB タブと同じ構成であり、同じ理由で選んでいる ── 自動化から git を触れる、GUI がその部品で
組める、**AI が git を触れる**（許可されたときだけ）、GUI 自身を Lua で自動化できる。

---

## 1. 対象の指し方 — パスを組み立てさせない

`caps.rs` の原則は「スクリプトはパスや URL を組み立てられず、登録された名前しか呼べない」。
git も同じ原則に従うが、**リポジトリの窓口を設定に登録させるのは重い**（作業フォルダは
increase するし、ワークスペースを作るたびに1つ増える）。

そこで**既にある名前**を使う:

```lua
git_status(tab)      -- そのタブの作業フォルダのリポジトリ
git_status()         -- 呼んだ側のタブ
```

タブは自動化の語彙で既に「名前で指せるもの」（`TabRef`: 番号 / 表示名 / 自動化 ID）。
**リポジトリは「そこに居るタブ」で指す。** 生のパスは受け取らない。

- 作業フォルダを持たないタブ、git の管理下にないフォルダは、その旨のエラーを返す
- 作業フォルダの外は触れない。`-C <そのフォルダ>` を必ず付けて起動する

## 2. 層構造 — 生に降りられる限り安全

```
層1  読み  git_status / git_diff / git_log / git_conflicts
層1  書き  git_stage / git_unstage / git_commit / git_checkout / git_branch / git_merge
層1  生    git_run(tab, "引数…")        ← 土台。糖衣はこれを組み立てているだけ
────────────────────────────────────────────────────────────
層2  画面  上を呼ぶだけの薄い GUI（グループ + 行 + 行に紐づく操作 + 入力欄）
```

**判定ルール（DB と同じ）**: 生の口が常に隣にあり、`git_commit` はそれを組み立てる糖衣に
すぎない ── この関係が保たれている限り、糖衣をいくら足しても壊れない。逆に
「`git_commit` があるから `git_run` は要らない」となった瞬間に、GUI が天井になる。

**作らないもの**: リポジトリのモデル化（コミットオブジェクトの型、ref のグラフ、履歴の
遅延読み込み）。これらは「git を知らなくていい」という約束を売るもので、その約束は
rebase・submodule・LFS・detached HEAD で必ず破れる。破れたときには結局生の口が要る。

## 3. 何を画面に出すか — 出す/隠す/出さない の3段階

参考にした SCM 統合は、**登録している操作が約200、画面に出しているのは十数個**だった。
残りはコマンドパレット（名前を知っている人だけが届く場所）で、さらに「登録するが既定では
出さない」段階まである。この配分そのものが「基本は画面、高度はコマンド」の実装形である。

**最初に画面へ出すのは5つだけ**:

| 出す | 理由 |
|---|---|
| 変更の一覧（未ステージ / ステージ済み / 衝突） | 端末で `git status` を読むより確実に速い |
| 差分を見る | 端末で読めない領域。GUI が構造的に勝つ |
| ステージ / 解除 | 一覧があれば1クリックで済む |
| コミット（メッセージは AI 生成、§5） | このアプリの独自価値がここに乗る |

**出さない**: pull / push / ブランチ切り替え / stash / tag / rebase / cherry-pick / reset。
プリミティブとしては層1にあり、Lua からもコマンドからも呼べる。**画面に出すかは、使ってから
決める。** 先に全部出すと、二度と減らせない。

**絶対に画面へ出さない**: `reset --hard`・force push・`clean -xdf`。これらは
「押し間違いが取り返せない」側にあり、端末で打つ手間が最後の確認になっている。

## 4. 安全 — 止めるのではなく、別の道を出す

参考にした実装で最も良かったのは、**保護ブランチへの直接コミットを拒否せず「新しいブランチを
作りますか」と代替を出す**設計だった。禁止は人を迂回させるが、代替は人を正しい道に乗せる。

- **`git_*` は自動化の権限で既定「人間だけ」**。AI に開けるなら読み（status / diff / log）から
- **`git_run` は既定で人間だけ**、かつ画面には出さない。ここを開けることは
  「AI に git の全権を渡す」と同義なので、権限表の1行として明示的に選ばせる
- **保護ブランチ**（既定: `main` / `master`）へ直接コミットしようとしたら、止めて
  「新しいブランチを作って、そこへコミットしますか」を出す
- **走るものは見せる**（RULES）。GUI が組み立てた git のコマンド行は、実行と同じ関数で
  組み立てたものを、そのまま人が読める場所に出す

## 5. AI が書く・AI が直す

**コミットメッセージ** ── 新しい道を作らない。自動化エディタが Lua を書かせている既存の経路
（`ai_engine` / `suggest_with_local_ai`）に、差分を渡してメッセージを返させるだけ。
使う AI の選択もその設定を共有する。

**コンフリクトの解決** ── Rust に「マージ解決モード」を作らない。**ラリー（受け渡し + 審判）の
再利用**で、Lua テンプレートとして書く:

```
git_conflicts(tab) で衝突ファイルを取る
  → 内容を exchange に置いて AI に渡す
  → 返ってきたものを書き戻す
  → 人が差分を見る
  → git_stage
```

**守る線が1本ある: AI が解決したものを、人が差分として見る前にコミットしない。**
解決の提案までが AI の仕事で、確定は人の仕事。ここを自動で通すと、
「気づいたら片方の変更が消えていた」が起きたときに、誰にも追えない。

## 6. `repo.rs` の線を守る

`repo.rs` / `pr.rs` は **git を起動せず**、`.git/HEAD` を直接読む。だから rebase 中で
`index.lock` が握られていてもサイドバーは答えられる。**この経路は今のまま残す。**

`git_*` は git を起動する（status も diff も、正しく取るには git 自身が要る）。
つまりアプリの中に読みの経路が2本になるが、これは重複ではなく**役割が違う**:

| | 起動しない読み（`repo.rs`） | 起動する読み（`git_*`） |
|---|---|---|
| 何のため | 常時表示（ブランチ名・PR・色帯） | 人が開いたときの一覧と差分 |
| いつでも答えるか | **答える**（ロック中でも） | 答えないことがある（それでよい） |
| 呼ぶ頻度 | 毎ティック | 人が開いたとき |

**混ぜてはいけない。** サイドバーの表示を `git_*` に置き換えると、rebase 中に
ブランチ名が消える ── 今持っている保証を、便利さのために捨てることになる。

## 7. 名前は平らにする（`git.status` ではなく `git_status`）

DB の設計メモでは `db.query(...)` と書いていたが、**入れ子のテーブルは採らない。**

`shikisha` テーブルの**トップレベルの関数**であることが、この app では load-bearing になって
いる:

- `primitive_names()` はトップレベルの関数だけを列挙する
- **自動化の権限**（`grants::CATALOG`）はその名前を鍵にしている
- 外部 API の `method` も、`list` の答えも、同じ名前を使う

入れ子にすると、この3つから同時に姿を消す ── 権限表に出ず、`list` に載らず、外部 API から
呼べない。**`git_status` / `db_query` と平らに書く。** DB を実装するときも同じ。

## 8. 却下した案

### git を起動せず、自前で読む
**却下。** `.git/HEAD` の直読みは「ブランチ名」だから成立する。status は index の形式、
diff は差分アルゴリズム、log は履歴の走査で、どれも git の再実装になる。
**保証を上げるどころか、静かに間違える経路を作る。**

### リポジトリを設定の窓口として登録させる（DB と同じ形）
**却下。** DB の接続は数個で寿命が長いが、作業フォルダは増減する。
**既にある「タブ」という名前で指せば、登録という手間ごと消える。**

### 画面に全部出す（pull / push / ブランチ / stash / tag …）
**却下**（§3）。減らせなくなる。参考にした実装が200のうち十数個しか出していないのは、
機能が足りないからではなく**そう決めているから**である。

### AI にコンフリクト解決からコミットまでやらせる
**却下**（§5）。提案までが AI、確定は人。

### 履歴の組み替え（interactive rebase / cherry-pick / reset）を GUI に載せる
**却下。** 参考にした実装でも本体には無く、別レイヤに置かれている。
**端末で打つ手間が、最後の確認になっている。**

- worktree を作る導線（別件。ここでは扱わない）
- コミットメッセージ生成に渡す差分の上限（巨大な変更をそのまま渡さない）
