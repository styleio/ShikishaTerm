# 案内 (？ を押すと答える AI)

歯車の隣の **？** を、手引きへのリンクから **その場で答える相手**に変える。
このソフトの使い方と設定のしかたに答え、設定の画面まで連れて行き、
選ばれた入力欄に代わりに書き込む。答えるのは「設定 > 基本 > アシスタントAI」に
選ばれている AI。

この文書は着手前の設計メモで、決まったことと、なぜそう決めたかを残す。

---

## 1. 腐らせないための骨組み

AI が参照するものを人が書くと、書いた日から古くなる。しかも**古いまま答える**ので、
誰も気づかない。だから参照するものは全部、**機械が読める元から毎回作る**。

| 層 | 中身 | 元 | 正確さ |
|---|---|---|---|
| **画面の地図** | 設定の画面 30 枚（id・名前・副題） | `webui::PAGE` の `globalSections()` / `deskSections()` | 完全（一覧をそのまま読む） |
| **設定の言葉** | `settings.*` の文言 1100 あまり（項目名・ヒント） | `lang/<code>.json` | 完全（画面がそこから描かれている） |
| **どの画面の言葉か** | 言葉 → 画面 の結び付き | 上の2つを突き合わせる（§2） | 6割弱が確定。残りは画面を名乗らない |
| **キーと権限** | `Ctrl+B` の一覧・自動化の権限表 | `keys::listing()` / `grants` のカタログ | 完全 |
| **手引き** | 画面の案内・はじめ方・困ったとき | `docs/MANUAL.*.md`（人が書く散文） | §4 の門番が見張る |

**人が書く場所は最後の1つだけ**で、そこも「名指しした物が実在するか」を
テストが照合する。

## 2. 言葉がどの画面のものかを、どうやって知るか

`globalSections()` は `{id:"remote", label:T["settings.sec.remote"], build:remoteCard}`
という並びで、`deskSections()` も同じ形をしている。だから **`build` に書かれた関数から
辿れる `T["..."]` が、その画面に出る言葉**になる。

辿る深さは **2**。ただし**最初の一歩より先では、3 画面以上から呼ばれる関数は
共有の部品**とみなして辿らない。これを入れないと、`el` や `row` のような
全画面共通の部品を通って、全部の言葉が全部の画面に結び付いてしまう（実測: 除外なしの
深さ3 で `settings.bring.*` の 43 語が 14 画面に属した）。

最初の一歩を除外の対象にしないのは、**その画面自身が呼んでいるものは、他が何枚
呼んでいようとその画面のもの**だから。実際、除外していた間は git の画面が 5 語
（`gitFields` が共有扱いで切られていた）しか持てなかった。

実装での実測:

| | |
|---|---|
| 画面 | 30 |
| 画面に結び付いた言葉 | 663 / 1117 |
| 2画面に属する言葉 | 65 |
| 3画面以上に属する言葉 | 9 |
| 言葉が1つも無い画面 | 0 |

結び付かなかった 454 語は、**画面を名乗らずに索引へ入れる**。
嘘の在り処を言うより、在り処を言わない方がよい。

**静的には取れないものがある。** `T["settings.dsec." + id]` のように名前を組み立てて
引いている 143 語は、文字としてどこにも書かれていない。これは限界として認め、
「全ての言葉が画面を名乗る」ことは要求しない（要求すると、人が手で注釈を足し続ける
仕組みになり、それこそが腐る）。

## 3. 出口は3つ、元は1つ

同じ索引から3つ出す。**写しは1枚も作らない。**

- **AI が読む索引** … `/api/guide`（JSON）。？ のパネルが質問と一緒に渡す
- **人が読む事典** … `docs/SETTINGS.md` / `SETTINGS.ja.md`（生成物、リポジトリに入れる）。
  `site/scripts/sync-docs.mjs` がサイトへ流す
- **手引きへの差し込み** … `docs/MANUAL.*.md` の `<!-- guide: <画面のid> -->` の行が、
  生成時にその画面の項目一覧に置き換わる

事典をリポジトリに入れるのは、サイトの生成が `docs/` しか読まないから。
入れる以上は古くなりうるので、§4 の門番が要る。

## 4. 門番 (テスト)

| 落ちる条件 | なぜ |
|---|---|
| 生成した事典が、入っている `docs/SETTINGS*.md` と違う | 生成を回さずにコミットした |
| 画面の一覧に載っている画面の言葉が0 | カードの名前が変わった・中身が消えた |
| 手引きが名指しした画面の id が地図に無い | 画面が消えた・名前が変わった |
| 手引きの差し込みの印が、地図に無い画面を指している | 同上 |
| `settings.*` の言葉が `lang/en.json` に無い | 既存の `every_word_a_page_asks_for_exists` が見る |

事典を書き直すのは `cargo test -p shikisha-core --features write-docs` ではなく、
**`SHIKISHA_WRITE_DOCS=1 cargo test guide` で書き直す**（環境変数の方が、
features を増やさずに済む）。

## 5. ？ のパネル

**置かれるページにする**（`runtime::SettingsPlace` と同じ仕組み）。盤面の中に
HTML で浮かべると、設定を全面で開いた瞬間に隠れる —— 設定を案内するための
パネルが、設定を開くと消えるのでは意味がない。

- 矩形はアプリが持ち、掴んで動かせる。動かしている間は枠だけを動かし、
  離したところで本体を置き直す（ネイティブの子ビューを毎フレーム動かすと
  Windows では引きずる）
- 置き場所は `data/`（消えても困らない）
- スマホでは浮かせない。下から出るシート（狭い画面で浮かせると、
  指のドラッグが画面のスクロールと取り合いになる）

## 6. 連れて行く (操作は必ず聞く)

答えの中で画面を名指しできるようにする。名指しに使えるのは **§1 の地図にある id だけ**。

押すまで何も起きない。AI の答えの下に「設定 > リモート接続 を開く」という
ボタンを1つ出し、**押すのは人**。これは既存の「呼びかけの帯」と同じ作法で、
台本が人に頼むときの形をそのまま使う。

## 7. 代わりに書き込む (黄色い枠)

？ を開いている間、設定の画面の入力欄を押すと、その欄が**選ばれた欄**になる。

**欄が何であるかは、描かれている画面から読む。** 索引からではない —— 目の前の
DOM が、その人が見ているものそのものだから、ズレようがない。欄の入っている
`.row` の `<label>` と、その下の `.hint`、入力の種類（文字・数・チェック・選択）を
そのまま渡す。

- **値は渡さない。** 渡すのはラベルと種類だけ。パス・ホスト名・アカウント名が
  AI の会社へ出るのを既定にしない
- **秘密の欄は選べない。** `type=password` の欄、`secrets` の欄、トークンの欄は
  選択の対象から外す。AI が書いた文字列がそこへ入る道を作らない
- **保存は人が押す。** 書き込んでも「未保存」になるだけなので、確認の仕掛けを
  別に作らなくても、既にある門が効く

## 8. 深いところを知りたいとき

索引が答えを持たない種類の問い（なぜこう動くのか、このエラーは何か）のために、
**人が押したときだけ**、道具付きの AI に調べさせる道を残す。既定では通らない。
速さと費用が一桁変わる（軽い呼び方で claude 約1,400トークン、道具付きで約9,500）。

## 9. やらないこと

- **AI 用のマニュアルを手で書く。** 書いた日から古くなる
- **実行時に GitHub を読ませて答える。** 腐らないのは索引と同じだが、
  遅く・高く・不正確になる（700KB の画面のコードから小さなモデルが推測する）
- **画面の言葉を索引に写す。** 索引は辞書と画面から毎回作る
